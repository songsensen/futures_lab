# /admin 后台录入说明与数据关系图

本文档说明 `/admin` 后台里各张表怎么录、按什么顺序录，以及所有数据类型之间的关系。
时间序列表（日线行情/持仓/仓单/基差/宏观数据）走 `flask import-xxx` 命令行导入，
不在 `/admin` 里，用法见 `import_templates/README.md`。这份文档只讲 `/admin` 覆盖的表。

## 一、怎么打开、怎么看

本地启动后访问 `http://localhost:5000/admin/`（部署到别的机器就把 localhost 换成对应地址）。
顶部导航栏按四个分类分组，对应下面四个模块：

- 品种基础信息：品种、生产端工艺/产地、上下游产业链、因素标签、品种关注点
- 行情：合约、月度利润率
- 案例库：历史案例、案例时间线、事前状态观察
- 事件与政策：事件、政策

每张表都是标准的四件套：列表（List，可搜索）、新建（Create）、编辑/删除（列表每行前面的铅笔/垃圾桶图标）。
凡是外键字段（比如"所属品种""关联案例"），表单里都是下拉框，下拉框里显示的是可读文本
（比如"SA 纯碱""2025年纯碱反内卷预期行情"），不是内部数字 ID，选错了也容易一眼看出来。

目前后台没有登录鉴权，谁能打开这台机器的这个地址谁就能改数据，先不加是因为项目还是单机单用户在用。

## 二、建议的录入顺序

有外键依赖的表，先建"被指向"的那张表，再建"指向它"的表，否则下拉框里根本没有可选项。
建议顺序：

1. **品种（variety）** —— 几乎所有其他表都直接或间接挂在它下面，最先建。
2. **因素标签（factor_tag）** —— 不依赖品种，是全局共享的标签库，可以和品种同时建，随时补充新标签。
3. **生产端工艺/产地（production_route）、上下游产业链（supply_chain_node）、品种关注点（variety_factor）**
   —— 都需要先选一个已存在的品种；`variety_factor` 还需要选一个已存在的因素标签。
4. **历史案例（case）** —— 需要选品种，可选选一个主驱动因素标签。
5. **案例时间线（case_timeline）** —— 需要先有对应的案例。
6. **事前状态观察（setup_episode）** —— 需要选品种，如果这次极端状态最终催生了某个案例，
   还要把"是否催生了案例"这个下拉框指到对应的案例（留空就是反例，代表到过极端但没催生事件）。
7. **事件（event）** —— 品种可留空（宏观事件），因素标签可选，如果这条事件是某个案例的"锚点"
   （案例开始被市场公开注意到的那个点），把"关联案例"指过去，指的是第4步已经建好的案例。
8. **政策（policy）、月度利润率（profit_margin_record）、合约（contract）** —— 相对独立，随时可以建，
   不强依赖前面几步（`profit_margin_record` 需要选品种）。

## 三、各类数据之间的关系

### 3.1 品种（variety）是唯一的中心表

品种基本信息本身（交易所、板块、定价权归属类型、成本区间、库存耐储存性等）存在 `variety` 表里，
向外辐射出四条链路：

- **品种画像链**：`production_route`、`supply_chain_node`、`variety_factor`（再关联到 `factor_tag`）
- **行情链**：`contract` → 下面挂日线行情/持仓龙虎榜/仓单/基差（这四张走 CSV 导入，不在 `/admin`）
- **案例链**：`case` → `case_timeline`；`case` 还被 `setup_episode.led_to_case_id` 和 `event.case_id` 反向引用
- **独立于品种之外、全局共享的表**：`factor_tag`、`macro_data`（CSV导入）、`policy`

### 3.2 生产端工艺/产地 vs 上下游产业链 —— 都是品种画像的一部分，但回答不同问题

`production_route` 回答"这个品种自己是怎么生产出来的"：一个品种可能有几条并行的工艺路线
（纯碱的联碱法/氨碱法/天然碱法）或原料产地（豆粕的巴西/美国/阿根廷大豆），每条路线记市场占比、
现金成本、是否只产这一个品种、有没有副产品（副产品还盈利的话，主产品低价能维持更久）。

`supply_chain_node` 回答"这个品种的成本从哪来、成本又占下游多少"：上游节点是原料，下游节点是需求方，
`direction` 字段区分方向，`cost_share_pct` 的含义随方向变化（上游=占该品种成本的比例，
下游=该品种占下游产品成本的比例，两者不能跨节点直接相加）。

### 3.3 事件（event）vs 历史案例（case）—— 粒度完全不同

这是最容易搞混的一组，之前单独讨论过，这里整理进文档：

`event` 是细粒度的"某一天发生了什么"记录，字段很薄（日期、标题、说明、分级、来源），
服务于两处：K线图上打标注点、日历时间线列表。数量会很多，大部分事件只是日常记录，
不会发展成一段完整值得复盘的行情。

`case` 是完整的一段历史行情复盘，字段厚得多：开始/结束日期、价格起点/极值/终点、
当时的库存/需求/盈利状态分类、市场当时的主流解读和复盘后判断的真实驱动（故意拆成两个字段，
两者不一致的案例最有参考价值）、是否失败案例、催生机制。是"历史相似案例匹配"功能的数据源。
`case_timeline` 是案例下面的分阶段时间线（预期炒作期/情绪消退期/现实回归期）。

两者的连接点是 `event.case_id`：如果某条事件是某个案例的"锚点"，就把这条事件关联到对应案例，
K线图上就能区分"这只是条普通事件"还是"这是某个案例的起点"。**这个关系只能从事件这一侧设置**
——事件表单里有"关联案例"下拉框，案例表单里没有反过来"关联哪些事件"的字段，
因为案例模型没有定义指向事件的反向关系，不需要在案例详情里维护一份事件清单。

### 3.4 事前状态观察（setup_episode）vs 历史案例（case）—— 反例也要记

`setup_episode` 记录的是"品种价格或利润走到极端状态"这件事本身，不管后来有没有发展成案例。
`led_to_case_id` 留空 = 到过极端但什么都没发生的反例，有值 = 后来确实演变成了对应的案例。
两种都要记，才能算出一个诚实的"这种极端状态历史上有多大概率催生事件"的基础比率，
不然只看"催生了事件"的正例，会让人误以为极端就一定会反转，这是案例库设计上特意要避免的偏差。

### 3.5 时间序列表和 `/admin` 表怎么分工

日线行情、持仓龙虎榜、仓单、基差、宏观数据这五张表是"每天/每月追加一批新行"的高频数据，
天然适合批量导入，走 CSV + `flask import-xxx` 命令，不在 `/admin` 里维护，
具体格式见 `import_templates/README.md`。

其余所有表（品种画像、案例库、事件、政策，以及看似简单但更新频率低的合约、月度利润率）
都需要人工判断或者更新频率低，在 `/admin` 里一条条录入更合适。

## 四、快速参照表

| 表（中文名） | 后台分类 | 必须先有的外键 | 常见用途 |
|---|---|---|---|
| 品种 | 品种基础信息 | 无 | 所有品种画像/行情/案例的挂载点 |
| 因素标签 | 品种基础信息 | 无 | 品种关注点、案例、事件共用的标签库 |
| 生产端工艺/产地 | 品种基础信息 | 品种 | 工艺路线或原料产地的占比/成本/副产品 |
| 上下游产业链 | 品种基础信息 | 品种 | 上下游节点及成本/需求占比 |
| 品种关注点 | 品种基础信息 | 品种、因素标签 | 该品种该盯哪些因素、当前状态 |
| 合约 | 行情 | 品种 | CSV 导入行情数据时会自动创建，一般不用手动建 |
| 月度利润率 | 行情 | 品种 | 按月记录简化利润率数值 |
| 历史案例 | 案例库 | 品种，可选因素标签 | 完整行情复盘，情景匹配的数据源 |
| 案例时间线 | 案例库 | 历史案例 | 案例演绎过程的分阶段节点 |
| 事前状态观察 | 案例库 | 品种，可选历史案例 | 极端状态记录，含正例反例 |
| 事件 | 事件与政策 | 可选品种/因素标签/历史案例 | K线标注 + 日历列表 |
| 政策 | 事件与政策 | 无 | 政策监控清单 |
