# 大宗商品期货分析系统 — 粗略框架（测试数据版）

这是把我们讨论的分析框架先跑通的一个骨架版本，所有数据都是**测试/模拟数据**，
目的是验证整个链路（品种信息 → 现状体检 → 历史案例匹配 → 页面展示）能不能真正串起来，
不是为了数据准确。

## 怎么运行

```bash
pip install -r requirements.txt
python run.py
```

首次启动会自动建库并灌入测试数据（3个品种：纯碱SA、玻璃FG、豆粕M，约3年模拟日线 + 6条历史案例），
之后打开 http://127.0.0.1:5000 即可。

如果想清空重来：`python seed_db.py --reset`

## 这个骨架具体落地了哪些讨论过的点

- **共用标签体系（FactorTag）**：品种的"关键关注点清单"和历史案例的"驱动因素"用的是同一张标签表
  （`app/models.py` 里的 `FactorTag`），这是让两个模块互相指认的接口，不是各自一套文字描述。

- **现状体检**：品种详情页的"现状体检"卡片，把价格历史百分位、持仓历史百分位、虚实盘比、
  基差都算出来展示，而不是一段静态介绍文字（`app/analysis.py` 的 `get_price_snapshot` /
  `get_position_snapshot` / `get_basis_snapshot`）。

- **关注点清单 + 实时状态**：每条关注点会显示"平静 / 偏热 / 异常"，判断逻辑是看最近60天内
  有没有命中同标签的 Event，或者价格是否处于历史极端分位（`compute_factor_status`）。这是一个
  规则性的启发式，不是智能算法，说明这一点很重要。

- **历史情景匹配**：不是只按价格位置匹配，而是"当前激活的因素标签 + 基本面状态桶"组合打分
  （`match_historical_cases`），匹配分数和理由都会显示在页面上，方便你判断这个匹配靠不靠谱。
  如果没有案例过线，会诚实显示"没有找到直接相关的历史案例参照"，不会硬凑。

- **案例库里"市场解读 vs 真实驱动"拆成两个字段**：`Case.market_interpretation_then` 和
  `Case.real_driver_after_review`，两者不一致时案例详情页会高亮显示（讨论里提到这类案例最有价值）。

- **避免幸存者偏差**：`Case.is_failure_case` 专门标记"逻辑没兑现"的案例（比如种子数据里
  2025年纯碱反内卷案例，就是一个典型的"喊话没落地、行情最终回吐"的失败案例），案例列表和
  详情页都会显示这个标签。

- **虚实盘比警戒**：持仓/仓单分析页对照了讨论里提到的100:1警戒阈值，超过会标红提示。

- **K线图事件标注**：品种详情页的K线图上，历史案例的起点和最近的模拟资讯事件都会以标注点的
  形式打在对应日期上，鼠标悬浮能看到事件标题和因素标签。

- **事前状态信号（事件是"催生"出来的，还是纯粹外生冲击）**：很多事件不是随机冲击，而是价格/
  筹码/基本面走到极端后被动"挤"出来的结果——等新闻出现再反应经常已经晚了。`Case` 表新增了
  `trigger_origin`（催生型/外生冲击型）和 `precipitating_mechanism`（资金布局型/物极必反型/
  容忍阈值型），并且新增了 `setup_start_date`/`setup_description`/`pre_event_chip_anomaly`
  字段，记录极端状态从什么时候就已经开始、比事件被市场注意到早了多久。新增的 `SetupEpisode`
  表专门记录"事前极端状态"的正反例——不只是记录"后来真的催生了事件"的案例（否则会有幸存者
  偏差，让人误以为极端就一定会反转），也刻意保留了"同样极端但什么都没发生"的历史记录。
  品种详情页的"事前状态信号"卡片（`compute_setup_signal` / `match_setup_precedents`）会用
  只看当天及之前数据的扩展窗口百分位（避免用未来数据判断过去，参见 `_expanding_percentile_series`），
  算出当前价格已经连续多少天处于历史极端分位，再拿这个持续天数去匹配 `SetupEpisode` 历史库，
  给出一个"历史上类似情况有多大比例最终催生了事件"的诚实转化率——是基础概率，不是预测。

## 目录结构

```
futures_lab/
  app/
    models.py          数据模型（品种/因素标签/关注点/行情/持仓/仓单/基差/案例/事件/宏观/政策）
    analysis.py         分析引擎（百分位计算、虚实盘比、关注点状态、历史案例匹配）
    seed.py              测试数据生成（3个品种，约3年模拟行情 + 6条案例）
    blueprints/          按模块拆分的路由（main品种 / case案例库 / calendar日历 / position持仓 / principles原则）
    templates/           页面模板（Bootstrap + ECharts，走服务端渲染）
  run.py                 启动入口（自动建库+灌测试数据）
  seed_db.py              手动重建/重新灌入测试数据
```

## 后续怎么把测试数据换成真实数据

- **行情/持仓/仓单/基差**：把 `app/seed.py` 里生成数据的部分，换成从交易所官网爬取或数据商
  接口获取的真实数据写入同样的表结构，`analysis.py` 和所有页面完全不用改。
- **历史案例**：这块是研究/写作性质的工作，没法自动化，需要按 `Case` / `CaseTimeline` 的字段
  模板手工整理（可以参考期货公司年度复盘报告作为素材来源），录入方式后续可以补一个简单的
  表单页面，现在先直接改 `seed.py` 里的案例定义作为"录入模板"参考。
- **用户系统**：现在完全没做鉴权，蓝图按模块拆分好了，以后要加登录/多用户，新增一个 auth
  蓝图并在 `app/__init__.py` 里注册即可，数据库表结构不需要大改。

## 现在明确没做、后续再看的部分

- 品种对比工具、更完整的日历视图（现在是列表形式）、案例录入表单页面——这些不是这次讨论的
  核心两个功能（品种信息+关注点、历史案例参照），先跳过，跑通核心链路优先。
- 情景匹配算法是简化的规则打分，不是任何机器学习模型，样本量也很小（每个品种2条案例），
  跑起来看的是"链路通不通"，不是"匹配得准不准"——这个预期在前面讨论可行性的时候已经说清楚了。
